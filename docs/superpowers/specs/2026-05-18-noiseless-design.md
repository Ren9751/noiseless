# noiseless 設計書

- 作成日: 2026-05-18
- ステータス: 設計レビュー中
- 仮称: `noiseless`（実装時に再検討可）

---

## 1. 概要

`noiseless` は、自分の関心に最適化されたタイムライン型 Web アプリ。コンセプトは「ノイズのない X」。

商用 SNS が「滞在時間」を最適化指標にするのに対し、本アプリは「あなたの関心」を最適化指標に置き換える。

### 1-1. 位置づけ

AI サービス開発ゼミでのプロダクト構想として実装する。商用プロダクト（Particle, Feedly Leo など）が「マス向けの個人最適化」を目指すのに対し、本アプリは「完全に 1 人最適化」に振り切る。商用が踏み込めない最適化を、自作だからこそ実現する。

### 1-2. メッセージング

- ノイズが少ない情報源を、自分専用に作る
- 使うほど、自分の関心に合わせて精度が上がる
- 滞在時間を最大化しない。フィードは有限で、読み終わったら終わる
- フィルターバブル対策として、関心の隣接領域も意図的に混ぜる

---

## 2. 想定する体験

朝、アプリを開く。タイムラインに 30〜50 件の記事が、自分の関心スコア順に並んでいる。タイトルと、X の投稿 1 個分くらいの短い本文が並ぶ。スクロールしながら読み進め、気に入った記事には「いいね」を押す。記事を読み切ると「今日は以上です」で打ち切られる。

数日〜数週間使い続けると、自分が押した「いいね」の傾向が学習され、上位に並ぶ記事が自分用にチューニングされていく。

時折、タイムラインの中段に「↗ 関心の隣接領域」のバッジ付きで、いつもなら読まないが関連のある記事が混ざる。これがフィルターバブル対策。

---

## 3. システム全体アーキテクチャ

バッチ処理（記事収集・スコアリング・埋め込み生成）とフロントエンド（タイムライン表示）を分離する。

```
┌────────────────────────────────────────────────┐
│  GitHub Actions (TypeScript, cron で1日2-3回)   │
│  ────────────────────────────────────────────   │
│  Step 1: 収集                                    │
│  Step 2: 本文取得 (Readability で抽出)           │
│  Step 3: スコアリング (Claude Haiku)             │
│  Step 4: 埋め込み生成 (Voyage AI voyage-3)        │
│  Step 5: 個人化スコア計算                        │
│  Step 6: セレンディピティ枠選出                  │
│  Result → Supabase に書き込み                    │
└────────────────────────────────────────────────┘
                   │
                   ▼
        ┌────────────────────────┐
        │  Supabase (PostgreSQL) │
        │  + pgvector 拡張        │
        └────────────────────────┘
                   ▲
                   │
┌────────────────────────────────────────────────┐
│  Next.js (App Router) on Vercel                 │
│  ────────────────────────────────────────────   │
│  - タイムライン (スコア順表示)                  │
│  - いいねタブ                                    │
│  - 設定画面 (興味プロフィール編集)              │
│  - API Routes (いいね保存、設定保存)             │
└────────────────────────────────────────────────┘
```

### 3-1. なぜこの分離か

- **GitHub Actions** は 1 ジョブあたり最大 6 時間まで実行可能で、数百件の LLM 処理に余裕がある
- **Vercel Cron Jobs** は無料枠だと 1 日 2 回・実行 60 秒の制約があり、本アプリのバッチには厳しい
- **Supabase** が両者の通信点として中央 DB の役割を果たす
- バッチ処理は `tsx` で TypeScript を直接実行できるので、Next.js 側と言語を統一できる

## 4. データモデル

Supabase (PostgreSQL) 上のテーブル。`pgvector` 拡張を有効化して埋め込みを保存。

| カラム | 型 | 説明 |

## 5. バッチ処理フロー

GitHub Actions で 1 日 2〜3 回実行。各ステップは関数として独立し、エラーで途中停止しても次の実行で再開可能。

### Step 1: 収集

各 `sources` の `kind` に応じたフェッチャを並列実行。

- `hatena`: RSS フィード経由（人気エントリー）
- `hackernews`: HN API（Top Stories）
- `reddit`: Reddit JSON API（指定サブレディット）
- `rss`: 任意の RSS URL
- `arxiv`: arXiv API（指定カテゴリ + 日付範囲）

取得した記事は URL で重複排除。`articles.url` に既存のものはスキップ。

### Step 2: 本文取得

各記事の URL に HTTP リクエストを投げ、HTML を取得。`@mozilla/readability` で本文抽出し、`body_excerpt` に保存。

- arXiv はアブストラクトをそのまま使う（HTML 取得は不要）
- RSS は feed の `content` を優先（取得済みなら HTTP リクエスト不要）
- HTTP 失敗、Readability 抽出失敗の記事は **タイムラインに出さない**（本文取得失敗は品質判定として除外）

### Step 3: スコアリング

Claude Haiku に各記事を投げ、以下を一度に生成:

- `prompt_score`（1-10）
- `summary`（X 風本文 140〜280字）
- `score_reason`（短文の評価理由）

構造化出力で安全にパース。`prompt_score` が閾値（例: 6）未満の記事は次のステップに進めない。

スコアリング用プロンプトの方針は life-repo の SCORING_SYSTEM_PROMPT を雛形にし、`user_profile.interests` から動的に組み立てる。

X 風本文の生成プロンプトは以下の要件を満たす:

- タイトルの言い換えではなく、内容を踏まえた本文にする
- 結論／一番面白いポイント／読む価値 のいずれかが伝わる
- 主張があるなら主張を、データがあるなら数字を、議論があるなら論点を入れる
- 絵文字・誇張表現・煽りは禁止
- 体言止め・断定は許可
- 日本語

### Step 4: 埋め込み生成

スコアが閾値以上の記事を Voyage AI（`voyage-3`）に投げ、1024 次元のベクトルを生成。`articles.embedding` に保存。

### Step 5: 個人化スコア計算

**Phase 1 では本ステップをスキップ**し、`final_score = prompt_score` とする。Phase 2 で以下を実装する。

ユーザーが過去にいいねした記事の `embedding` を取得し、その中心ベクトル（平均）を計算する。直近の関心を反映させるため、**最近 50 件のいいね** を優先的に使う（それ未満の場合は全件）。

新着記事との類似度（コサイン類似度）を `similarity_score` に保存。

`final_score` は以下のロジックで合成する:

- **いいね件数が 10 件未満の場合**: `final_score` は `prompt_score` のみで決まる（学習はまだ効かない）
- **10 件以上 50 件未満の場合**: `prompt_score` の貢献が約 7 割、類似度スコアの貢献が約 3 割
- **50 件以上の場合**: `prompt_score` と類似度スコアがほぼ同等の重みで合成

これにより、使うほど個人化が強くなる。具体的な重み（係数）は設定ファイルに切り出して、運用しながら調整できるようにする。

### Step 6: セレンディピティ枠選出

過去いいねの中心ベクトルとの類似度が「近すぎず遠すぎず」の帯（0.5〜0.7）の記事を候補とし、1 日 1〜2 件ランダムに選んで `is_serendipity = true` でマーク。

- 類似度 0.9 以上: 既に好きな領域そのもの（普通に上位に並ぶ）
- 類似度 0.5〜0.7: 隣接領域（セレンディピティ枠）
- 類似度 0.3 未満: 完全に無関係（ノイズとして除外）

---

## 6. 学習層

「使うほど自分用になっていく」を実現するロジック。**Phase 2 以降で実装**する。Phase 1 では `prompt_score` のみで並ぶ。

1. ユーザーがタイムラインで「いいね」を押すと `likes` テーブルに記録される
2. 次のバッチ実行時、`likes` の最近のレコードから「いいね中心ベクトル」が計算される
3. 新着記事と中心ベクトルの類似度が計算され `similarity_score` に保存される
4. `final_score` の計算式がいいね件数に応じて重み付けされ、徐々に学習主導になる

ユーザーから見ると、「使い始めは興味プロフィール通り」「数日後から少しずつ並び順が変わってくる」「数週間後には自分用に最適化されている」という体験になる。

---

## 7. セレンディピティ機構

評価順タイムラインだけだと、関心領域に近い記事ばかりが上位に来てしまう。これを意図的に崩すため、以下のロジックで「隣接領域」記事を挿入する。

- バッチで「隣接領域」記事を 1 日 1〜2 件選出（Step 6 参照）
- タイムライン表示時、セレンディピティ記事は強制的に 8〜10 番目あたりに挿入される
- `↗ 関心の隣接領域` バッジを付けて区別する

これにより「フィルターバブルを設計に組み込んで対策している」と説明可能になる。

## 8. UI / UX

### 8-1. 画面構成

3 画面だけで構成する。

1. **タイムライン**（メイン）
2. **いいね**（タブ切替）
3. **設定**（歯車アイコン）

### 8-2. タイムライン

- スコア順（`final_score` 降順）で 30〜50 件
- 各記事カードに表示するもの:
  - ソース名（例: `[はてブ]`, `[arXiv]`）
  - 取得時刻（相対表現、例: 06:34、昨日）
  - 原タイトル
  - X 風本文（140〜280字）
  - 評価理由（LLM が付けた短文、例:「AI 製品の経済性に影響」）
  - いいねボタン（♡、押すと赤くなる、消えない）
  - 出典 URL（小さく）
- セレンディピティ記事には `↗ 関心の隣接領域` バッジ
- 下までスクロールすると `── 今日は以上です ──` で打ち切り（無限スクロールしない）

### 8-3. いいねタブ

- 過去にいいねした記事を新着順で表示
- 同じカード UI

### 8-4. 設定画面

- 興味プロフィール編集（項目追加・重み調整）
- 特別ルール記述（自由記述）
- ソース管理（追加・削除・有効/無効）

### 8-5. インタラクションのこだわり

- いいねを押しても記事は消えない（X と同じ）
- 押した状態は視覚的に明確（♡ が赤に）
- スコア順は押した瞬間に変わらない（次のバッチで反映）
- 「Undo」「操作の予測可能性」を重視（CLAUDE.md の UI/UX 方針より）

## 10. MVP 範囲とフェーズ分け

### Phase 1: MVP

- ソース: はてブ、HN、arXiv の 3 つ
- ユーザー: 固定 1 人
- タイムライン表示（スコア順、有限スクロール）
- いいねボタン
- 設定 UI（興味プロフィール編集のみ）
- GitHub Actions で 1 日 2 回バッチ
- スコアリングはプロンプトのみ（埋め込みなし）

これだけでも「ノイズのないタイムライン」として動く。

### Phase 2: 学習層とセレンディピティ

- Voyage AI で埋め込み生成
- いいね中心ベクトルからの類似度計算
- 個人化スコアの合成
- セレンディピティ枠選出
- いいねタブ

### Phase 3: ソース拡張

- Reddit、任意の RSS、ニュースレター取り込み
- 設定 UI からソース追加・削除

### Phase 4: ゼミ発表後の拡張

- マルチユーザー対応（Supabase Auth 有効化）
- モバイル対応（PWA 化 / レスポンシブ強化）
- 関心マップの週次自動更新（LLM がいいね傾向を分析してレポート生成）
- Particle 風要素（要約モード切替、軽量ストーリー化）
- my-data 統合（goals.md, work-logs との連動）

## 11. 競合と差別化

### 11-1. 商用類似サービス

- **Particle (particle.news)**: AI ニュースリーダー。複数記事をストーリー化、Opposite Sides でフィルターバブル対策
- **Feedly + Leo**: RSS リーダーに AI 機能。フィードを手動購読する必要がある
- **Daily.dev**: 開発者向け AI 最適化フィード
- **Readwise Reader**: あとで読む + AI 要約 + ハイライト

これらは「マス向けの個人最適化」を目指している。

### 11-2. 本アプリの構造的優位

商用がビジネスモデル上できないこと:

- **完全に 1 人最適化**: 商用は規模を求めるため、最終的には「あなたに似た人」の集合最適化に近似する
- **専門領域（arXiv 等）の統合**: マス向けでは需要が薄く、商用は弱い領域
- **滞在時間を最適化しない**: 商用はエンゲージメント KPI と切り離せない

### 11-3. 本アプリの弱み

- UI / UX の洗練度では商用プロダクトに勝てない
- ストーリー化、マルチビュー要約などの高度機能はない
- 新規性が高いコンセプトとは言えない（個人最適化フィード自体は既存）

ゼミ発表では「商用が踏み込めない、完全な個人最適化を 1 人の問題として解いたツール」というナラティブで説明することを推奨。

## 12. 懸念点と対策

### 12-1. コールドスタート問題

学習層が効くにはいいね 10 件以上が必要。発表前に運用期間を確保しないと、ゼミデモで「学習が効いている」体験を見せられない。

**対策**:

- ゼミ発表の最低 2〜3 週間前から自分で使い始める
- 興味プロフィールのテンプレを最初から充実させる（life-repo の SCORING_SYSTEM_PROMPT を雛形に）
- 「学習が効いてる」ことを可視化する仕掛けを Phase 2 で入れる（例: いいね傾向ダッシュボード）

### 12-2. API コスト

1 日 200 件取得 × Claude Haiku スコアリング × 30 日 × 365 日 で、ある程度の課金が発生する。

**対策**:

- 1 次フィルタとして「カテゴリ・キーワードベース」の事前絞り込みを入れ、LLM に通す件数を半分以下に減らす
- Haiku の出力を構造化＋短くしてトークン数を抑える
- 毎月のコスト上限を環境変数で設定し、超えたらバッチ停止

### 12-3. 本文取得の失敗率

Cloudflare ブロック、有料記事のペイウォール、JS レンダリングが必要な記事は本文取得に失敗する。Phase 1 では失敗時スキップだが、想定よりフィード数が少なくなる可能性がある。

**対策**:

- Phase 2 でフォールバック方式を検討（タイトル + ソース固有メタだけで要約生成）
- ただし「本文未取得」バッジを付けて、ユーザーが品質差を認識できるようにする

### 12-4. メッセージング

「ノイズのない X」と謳うと「X というよりキュレートされたニュースフィードでは？」と突っ込まれる余地がある。

**対策**:

- 看板を「個人最適化された情報源」に振る
- 「X っぽい使用感を持ったタイムライン型情報摂取ツール」と説明する
