# オンボーディング & レベル適応 設計書

- 作成日: 2026-05-28
- ステータス: 設計レビュー中
- 関連: `2026-05-18-noiseless-design.md`（本体設計）

---

## 1. 目的

初めてアプリを使うときに、**興味分野**と**ITの理解レベル**を聞き取り、

1. 最初のレコメンド（タイムライン順位）を本人の興味に揃える
2. 本文（summary）の難易度を本人のレベルに合わせる

ことを実現する。順位は `interests` の重みで、本文の難易度は新しく持つ `it_level` で制御する。

---

## 2. 決定事項サマリ

| 項目 | 決定 |
|---|---|
| レベルの粒度 | 全体で1つ（分野別ではない） |
| レベルの段数 | 5段階（1=入門 / 2=初級 / 3=中級 / 4=上級 / 5=エキスパート）。本文難易度と1対1 |
| レベルの測り方 | **自己申告のみ**（各レベルに「本文の例文」を添えて選びやすくする）。ワードクイズ・±1補正は採用しない |
| 興味の集め方 | 用意したカテゴリ一覧から**タップで選ぶ**（自由入力ではない）。約80カテゴリ・10グループ |
| 難易度の適用 | **これから取り込む記事だけ**（既存記事は作り直さない） |
| 入口の挙動 | 初回は**必須**（完了するまでタイムラインに入れない） |
| 未完了時のバッチ | **そのまま動かす**（ガードは足さない／A案）。レベル空なら中級(3)で本文生成 |
| 初期化 | seed は `interests`・`it_level`・`special_rules`・`onboarded_at` を**すべて空**にする（`sources` は残す） |
| オンボーディング中のLLM | **呼ばない**（無料・即時・予測可能。例文は固定テキスト） |

## 3. データモデル変更

`user_profile` に2列追加する。新規マイグレーション `supabase/migrations/20260528000001_onboarding.sql`。

| カラム | 型 | 説明 |
|---|---|---|
| `it_level` | smallint | 1〜5。null=未設定 |
| `onboarded_at` | timestamptz | 完了日時。null=未完了。**ゲートの判定キー** |

- `it_level` の有無ではなく `onboarded_at` の有無で「完了」を判定する（途中離脱と区別するため）。
- 興味は既存の `interests`（jsonb）にそのまま書き込む。選んだ各カテゴリを `{topic, weight: 7}` として保存。重みは一律 7（後から設定画面の InterestEditor で調整可能）。

---

## 4. ゲーティング（入口の制御）

App Router の Server Component 側で `redirect()` する（ミドルウェアは使わない）。

- `app/page.tsx`（タイムライン）先頭で profile を取得し、`onboarded_at` が null なら `/onboarding` へ redirect。
- `/onboarding` ページは、`onboarded_at` が入っていれば `/` へ redirect。
- オンボーディング中は `Nav`（上部バー）を出さない。`/onboarding` を独自レイアウトにするか、`Nav` を出すかどうかをパスで分岐する。
- 判定の分岐（`onboarded_at` の有無で行き先を決める）は小さな純粋関数に切り出してテスト可能にする。

## 5. オンボーディング画面（2ステップ）

1枚のウィザード（クライアントコンポーネント、現在のステップを state で持つ）。上部に進捗（①→②）、各ステップに「次へ／戻る」。最後に1つの Server Action で保存。

### ステップ① 興味カテゴリ選択

- グループ見出し付きで約80カテゴリをタップ選択（複数可）。
- **最低1つ**選ばないと「次へ」を無効化。
- 選んだものが `interests` に重み7で入る。

### ステップ② レベル自己申告（例文プレビュー付き）

- 「入門／初級／中級／上級／エキスパート」を1つ選ぶ。
- 各レベルに「こんな人」の説明と、**そのレベルで書いた本文の例文**（固定テキスト）を添える。
- ユーザーは抽象的な用語ではなく、実際に出てくる文章を見て難易度を判断する。

### 保存

`completeOnboarding(interests, itLevel)` という Server Action を1つ用意。

- `interests`・`it_level`・`onboarded_at`（= now）を1回の update で書き込む（原子的）。
- 成功後タイムラインへ `redirect()`。
- 失敗時は画面にエラー表示・再試行可。

## 6. レベル → 本文難易度の反映

本文（summary）はバッチ実行時に `scripts/lib/scoring.ts` のプロンプトで生成・保存される。ここをレベルで切り替える。

### やること

1. `scripts/batch.ts`：スコアリングへ渡すプロフィールに `it_level` を追加（現状 `interests` と `special_rules` を渡している）。
2. `scripts/lib/scoring.ts`：固定の「中学生でも内容が伝わる、平易で親しみやすい日本語」を、レベル別の難易度説明に差し替える。
3. **`title_ja` は変更しない**（今回いじるのは本文だけ）。
4. レベルが null のときは **中級(3)** を仮の標準として使う（A案。DB由来の値は境界寄りで null は正当に起こる状態のため）。

### 5段階の書き分け（プロンプトに入れる文面）

| Lv | 想定読者 | 本文の書き方 |
|---|---|---|
| 1 入門 | ITをほぼ知らない | 専門用語・カタカナ語は避ける。使うなら必ず一言補足。日常の例えで。中学生でもわかる |
| 2 初級 | 「アプリ/サーバー/データ」は分かる | 基本語は前提。少し難しい語は短く補足。高校生〜文系大学生 |
| 3 中級 | 普段からIT記事を読む | API・DB・Git など一般的なIT用語は説明なしで使う。専門的な語だけ軽く補足 |
| 4 上級 | 現役エンジニア | 技術用語はそのまま。仕組みや背景に踏み込んでよい |
| 5 エキスパート | 研究者・上級者 | 最新の専門用語もそのまま。冗長な説明は省き、要点と含意を濃く短く |

140〜280字・絵文字や煽り禁止などの他のルールは現状のまま維持し、「誰に向けてどのくらい噛み砕くか」の部分だけがレベルで変わる。

## 8. 例文プレビュー（ステップ②で各レベルに添える固定テキスト）

同じニュース（「あるLLMに長期記憶機能が入った」）を5段階で書き分けた例。文面は後で磨いてよい。

- **入門**: AIが、前に話した内容を覚えていられるようになりました。今までは会話のたびに忘れていましたが、これからは「この前の続き」ができます。人と話しているような自然なやり取りに近づきます。
- **初級**: AIに「記憶」の仕組みが加わりました。これまでは会話ごとにリセットされていましたが、過去のやり取りを保存して後から参照できます。毎回ゼロから説明し直す手間が減ります。
- **中級**: LLMに長期メモリ機能が実装。従来はコンテキスト内の情報しか保持できなかったが、会話履歴を外部に保存して必要時に参照する。RAG的にユーザー文脈を永続化する形。
- **上級**: LLMの長期記憶を外部ベクトルストアへの非同期書き込みと検索で実現。会話ごとに embedding を生成・保存し、推論時に関連度の高い断片だけをコンテキストへ注入する。文脈保持とレイテンシのトレードオフ設計が肝。
- **エキスパート**: 長期記憶層を、書き込み時の embedding 生成と読み出し時の ANN 検索で構成。注入はトップ k に限定しテールレイテンシを抑える。課題は記憶の鮮度管理（古い文脈の減衰）と、検索ノイズによるハルシネーション誘発のトレードオフ。結果整合なストアだと読み書きの一貫性も論点になる。

## 9. 初期化（seed）

`scripts/seed.ts` を「未完了ユーザー」を作る形に変更する。

- `interests` → `[]`（空）
- `it_level` → 設定しない（null）
- `special_rules` → `''`（空）
- `onboarded_at` → 設定しない（null）
- `sources` → 現状どおり残す（はてブ / Hacker News / arXiv）。記事取得に必要なため。

これにより、自分自身を「初めて使う人」としてオンボーディングを通し、フローを検証できる。

## 10. エラー処理・エッジケース

| 状況 | 動き |
|---|---|
| 興味を0個で「次へ」 | ボタン無効（最低1つ必須） |
| 途中で画面を閉じた | `onboarded_at` が null のまま → 次回また最初から（途中保存なし） |
| オンボ済みで `/onboarding` を開く | `/` へ redirect |
| 未オンボでタイムラインを開く | `/onboarding` へ redirect |
| 保存に失敗 | 画面にエラー表示・再試行可（DB1回更新で原子的） |
| 未オンボのままバッチ稼働 | レベル空→中級(3)で生成、興味空→記事が薄くなるだけ（破壊なし） |

### 入力チェック（`completeOnboarding` 内）
- `interests` が1件以上
- `it_level` が 1〜5 の整数
- 既存 `updateInterests` と同様の境界バリデーション

## 11. テスト方針

vitest は設定済みだがプロジェクトのテストは0件。最初の数本を追加する。

- **純粋関数**: `buildPrompt` が `it_level` に応じて正しい難易度説明を含む（レベル別に検証）
- **バリデーション**: 興味0件・レベル範囲外を弾く
- **ゲート判定**: `onboarded_at` の有無で行き先が決まる純粋関数
- **手動確認**: seedでリセット → アプリ起動 → `/onboarding` へ遷移 → 選択して保存 → タイムラインに戻る → 設定画面に値が反映、をブラウザで通す

## 12. 既知の制約（スコープ外）

- **マルチユーザー化（Phase 4）との関係**: 本文（summary）は共有の `articles` テーブルに1つだけ保存されるため、「ユーザーごとに違う難易度」は現状の作りでは持てない。当面は固定1ユーザーなので問題ない。マルチユーザー対応時に、ユーザー別 summary 生成 or レベル別バリアント保存を別途設計する。
- **既存記事の難易度**: 「これからの記事だけ」方針のため、レベル変更前に取り込んだ記事の本文は古い難易度のまま残る。必要になれば `scripts/backfill-summaries.ts` で作り直せる（今回はスコープ外）。
