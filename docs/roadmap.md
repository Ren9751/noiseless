| P3 | 論文（arXiv）の扱い | 高度すぎてサラッと読めない問題。**決定: arXiv は `cs.CY` のみに絞る**（`cs.AI` を外す）。**実装済み**＝`scripts/seed.ts` と `fetchers/arxiv.ts` の `categories`/デフォルトを `["cs.CY"]` に変更 | ✅ 実装完了（2026-06-16） |
| P4 | 日本語記事の本文を LLM で書き直すか／生のまま出すか | 論点: コスト・原文ニュアンス vs 難易度とX風トーンの統一。**決定: 現状維持（全記事を常に Haiku で X風＋難易度に統一）**。トーンと難易度が全記事で揃うことを優先。Haikuコストは低い。→ 変更なし | ✅ 決定（2026-06-16） |
| P5 | 興味プロファイルを「初期選択＋いいね学習」で一本化するか | 初期興味（`interests`・重み付き）と Phase2 のいいね学習が現状は別レイヤー。**決定: 今は統合しない**。いいね学習層がまだ無いので、Phase2 でそれを作るときに一本化を一緒に設計する（YAGNI）。T10（dislike）と同時に検討 | ✅ 決定（2026-06-16） |
| P6 | レコメンドの方式をどうするか（いいね学習の根本設計） | **決定: ①プロンプト注入方式**。いいねした記事の傾向を短いテキストに要約し、毎回の採点プロンプト（`scoring-prompt.ts`）の頭に「最近こういう記事を好む」として注入する。検討した3案＝①プロンプト注入／②LLMにいいね履歴を読ませて毎回レコメンド／③embedding類似度（コンテンツベース）。**②は却下**＝バッチ毎の追加LLMパスでリクエスト数・出力トークン（律速）を圧迫。**③は却下**＝(a)1人用アプリなので協調フィルタリング(行動embedding)は他人がいなくて使えず、使えるのはコンテンツembeddingのみ (b)今のLLM採点が既に「意味的一致」を判断しており**仕事が被る**（二重計上）(c)embeddingの強み＝巨大候補プールの高速ランクが、今の「1本ずつ採点」規模では活きない。**③は将来候補が激増し「採点前に安く足切りしたい」ステージになったら、前段の足切りとして再検討**（被らず強みも活きる）。①は今のアーキ（採点と同時に title_ja/summary も生成する単一Haiku呼び出し）と素直に噛み合い、追加コスト・新基盤ゼロ。**P5（統合）・T10（dislike）はこの①の上で設計**する | ✅ 決定（2026-06-17・①プロンプト注入） |
| P7 | 記事の採点を「タイトルだけ」でやってよいか | 現状は本文抜粋（T12で800字cap）を Haiku に通して採点。**タイトルだけで評価すれば入力トークンが激減しコスト節約**になる。論点: タイトルだけだと精度が落ちる記事カテゴリ（論文・抽象的な見出し）がある／一方で大半の記事はタイトルで当たりがつく。**全件タイトル採点 / 1次タイトル＋2次本文の2段構え / 現状維持** のどれか。T12（本文cap）と同じコスト軸。**決定: ③現状維持**＝(a)律速は入力ではなく出力トークン・リクエスト数なので、入力を削るP7はボトルネックに効かない (b)`scoring.ts` の単一Haiku呼び出しが採点と同時に `summary`（本文を踏まえる要件）を生成しており、本文を捨てられない。捨てるなら採点と要約を2パスに割る必要があり、P6で却下した②に逆戻り (c)タイトルだけは論文・抽象見出しで精度が落ち、品質差別化（P1）を削る (d)T12で本文800字cap済みのため入力コストの削り代はわずか | ✅ 決定（2026-06-22・③現状維持） |
